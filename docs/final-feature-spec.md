## 2. 产品定位

### 2.1 一句话定位

Nasus 是一个面向存量系统增量迭代的 AI 原生质量闭环平台。  
它通过“项目空间 + 版本空间 + 个人工作空间 + 对话式 Agent”把系统画像、US 质量分析、测试资产生成、自动化执行、版本风险评估和上线后再基线化串成一个连续闭环。

### 2.2 产品要解决的问题

在存量系统中，版本迭代通常同时存在以下问题：

- 系统知识分散在 Git、US、文档、UX 图、历史测试资产里，团队无法形成稳定系统画像。
- 版本新增 US 后，质量工作往往只停留在临时测试任务，没有沉淀为后续可复用知识。
- 测试场景、范围、计划、用例、自动化脚本、性能脚本、变更文档和上线判断是分散完成的，缺少统一质量闭环。
- AI 可以提高产出速度，但如果没有对象模型、审批和证据链，很容易变成不可追溯的“会话式输出”。

Nasus 的目标不是做通用聊天工具，而是把 AI 变成版本质量工作的正式参与者。

### 2.3 核心产品原则

- **US 中心闭环**：质量工作围绕每个 US 展开，而不是停留在泛化任务列表。
- **系统画像是长期资产**：系统画像不是一次性导入结果，而是可基线化、可分支、可合并的长期知识对象。
- **对话优先，不等于无结构**：用户主要通过对话驱动 Agent 完成工作，但所有关键输出都必须落成结构化对象。
- **Agent-first，不等于绕过治理**：主会话是第一操作入口，所有业务动作都应支持 Agent 调用，但高风险动作仍必须进入确认、审批或策略闸口。
- **Agent Service 是系统主驱动层**：Agent 不只是对话 UI，而是负责目标理解、记忆管理、工具规划、多 Agent 并行调度和结果收敛的系统级服务。
- **工具是业务动作的正式接口**：项目、版本、US、执行、审批、同步和查询能力都要先定义成可被 Agent 调用的工具，页面按钮和表单只是同一工具体系的可视化封装。
- **Agent 负责规划，系统负责治理**：Agent 可以自主规划和调用 tools/skills，但正式结论、审批、基线写回仍由治理流控制。
- **版本分支像 Git 一样工作**：版本工作在系统画像分支上展开，上线后再把新知识合并回正式系统画像。
- **执行必须确定性**：测试执行、证据留存、审批和基线合并都必须具备确定性、可审计和可回放。
- **部署边界默认单租户**：当前默认产品形态是单企业内多项目平台，不是公网 SaaS 多租户产品；租户边界默认等同于部署边界。

## 4. 核心对象与分支模型

### 4.1 核心对象

| 对象 | 定义 | 默认归属 |
| --- | --- | --- |
| `Project Space` | 一个存量系统的质量主空间，承接长期知识、参与者和治理规则 | 项目级 |
| `System Image` | 从 Git、US、UX、OpenAPI、历史测试资产中抽取出的系统画像 | 项目级长期对象 |
| `Official System Image Branch` | 正式系统画像分支，是后续版本分支的源头 | 项目级正式基线 |
| `Version Branch` | 某次版本从正式系统画像分出的工作分支，承接版本增量知识和风险 | 版本级 |
| `US Work Item` | 版本中的一个 US 单元，绑定需求描述、责任人、相关系统对象和质量闭环状态 | 版本级 |
| `Quality Task` | 围绕某个 US 产生的一次具体质量任务或子任务 | US 级 |
| `Quality Asset Pack` | 围绕 US 形成的一组质量资产，包括测试场景、范围、计划、用例、自动化脚本、性能脚本、变更文档和变更方案 | US 级 |
| `Run` | 一次正式执行实例的 canonical 对象，当前阶段固定以 `execution_channel=web_runner` 交付 | 执行层正式对象 |
| `Evidence` | 执行结果、截图、日志、trace、归因、总结等证据对象 | 证据层 |
| `ToolDefinition` | 一个可被主 Agent 或 UI 统一触发的业务动作定义，描述输入、输出、风险和确认方式 | 产品级动作目录 |
| `ToolInvocation` | 一次具体的工具调用记录，连接对话、界面动作与后端领域对象 | 命令执行层 |
| `ToolResult` | 工具调用的结构化返回，包含摘要、对象引用、证据引用和后续推荐动作 | 结果封装层 |
| `AgentDecision` | Agent Service 或 Worker 产出的候选分析、归因、修复、放行或知识判断，状态为 `provisional / merged / approved / rejected` | 候选决策层 |
| `MergedResolution` | 由 `Merge/Score + Approval Control` 汇总形成的正式任务结论、正式放行建议或正式知识结论 | 正式治理层 |
| `Conversation Session` | 用户在项目空间、版本空间或个人工作空间中的一次对话工作会话 | 会话层 |

### 4.2 术语映射

为了兼容现有架构文档中的命名，产品术语与系统术语做如下映射：

| 产品术语 | 系统术语 |
| --- | --- |
| `System Image` | `Context Objects + Baseline` |
| `Official System Image Branch` | `Official Baseline` |
| `Version Branch` | `Version Working Baseline` |
| `Conversation Session` | `Session` |
| `US 质量任务上下文` | `Task Context Workspace` |
| `US 质量画像` | `Quality Assurance Profile` |

### 4.3 分支与合并规则

- `Official System Image Branch` 是所有版本分支的默认源头。
- 每个 `Version Branch` 必须从当前正式系统画像分支创建。
- 版本中新增的特性文档、测试场景、测试用例、Git 最新改动、执行结果和确认后的知识，先沉淀在版本分支内。
- 版本上线完成并审批通过后，版本分支中的新增知识才能合并回正式系统画像分支。
- 不同版本可以并行从同一个正式系统画像分支开出不同工作分支。
- 分支合并必须保留来源、证据、审批和差异说明。

## 5. 产品交互模型

### 5.1 对话优先的工作方式

Nasus 的主交互方式不是多页面表单流，而是“带结构化上下文的对话工作台”。

主会话不是辅助入口，而是第一操作入口：

- 用户可以直接通过主会话发起查询、分析、执行、审批申请、同步和治理动作。
- 主会话会把自然语言输入解析成 `ToolInvocationPlan`，再调用对应工具完成动作。
- 同一动作无论来自会话、按钮、表单还是卡片操作，本质上都应落成同一类 `ToolInvocation`。

每个空间都以一个主对话界面为中心，参考 AI Studio 的工作方式：

- 左侧是空间导航和对象切换。
- 中间是主对话画布，用于持续与 Agent 协作。
- 右侧是结构化上下文面板，展示当前项目、版本、US、系统画像、质量资产、执行结果和审批状态。
- 底部是主输入框，用户通过自然语言驱动任务闭环。

### 5.2 对话不是纯聊天

对话的作用是驱动工作闭环，而不是输出一次性文本。

对话输入默认会被理解为“需要规划和执行的业务动作”，而不只是文本问答。

每次对话都应尽量映射到以下结构化动作之一：

- 创建项目空间
- 导入系统原料
- 初始化系统画像
- 创建版本分支
- 导入版本级 US / Git 分支
- 分配 US
- 启动 US 质量分析
- 生成质量资产
- 触发执行
- 总结结果
- 发起放行审批
- 发起系统画像再基线化

这些结构化动作在系统内部必须先被定义成工具：

- 写操作以 `ToolInvocation` 作为 canonical command surface
- 页面按钮、快捷 chip、右侧卡片动作只是同一工具体系的 UI 封装
- 读查询可以保留 read API，但主业务动作不能只存在于 UI 表单里而无法被 Agent 调用

### 5.3 Agent Service、记忆与并行协作

Nasus 的 Agent 主体是系统级 `Agent Service`，而不是单个 LLM 调用。

Agent Service 必须包含：

- `Agent Supervisor`：把用户目标转成 `AgentGoal`，决定自主级别、预算、工具链和是否拆分并行子任务。
- `Agent Memory Manager`：统一管理短期工作记忆、会话记忆、项目长期记忆和候选知识。
- `Agent Goal Runtime`：围绕单个高级目标执行 Think -> Act -> Observe -> Decide 循环。
- `Agent Swarm Coordinator`：在复杂任务中并行调度多个 worker agent。
- `Agent Result Merger`：合并子 Agent 候选结果，识别冲突并提交给 `Merge/Score` 与审批链。

记忆分层固定为：

- **短期工作记忆**：单个 `AgentGoal` 内的当前目标、步骤、观察结果和预算。
- **会话记忆**：`ConversationSession` 内的最近消息、摘要 checkpoint、用户反馈和工具调用历史。
- **长期系统记忆**：系统画像、正式基线、历史质量资产、执行证据和已批准质量规则。
- **候选记忆**：Agent 发现但尚未确认的候选风险、候选关系、候选验证策略和候选失败归因。

并行 Agent 协作遵循以下规则：

- 大版本风险分析、多 US 质量评估、多模块影响分析和批量失败归因可以进入 Agent swarm。
- 每个子 Agent 都必须通过工具调用执行动作，并关联 `AgentGoal / ToolInvocation / Evidence / AuditEvent`。
- 子 Agent 只能产出候选结果；正式状态、正式放行、正式基线写回必须经过 `Merge/Score + Approval Control`。
- Swarm 必须受并发数、token 预算、工具调用次数和策略闸口约束。

### 5.4 对话交互示例

项目创建示例：

1. 管理员输入“我想创建一个新的项目”
2. Agent 回复“我可以为你创建项目，请提供 Git 仓库地址、US 文档、UX 图或 OpenAPI”
3. 管理员逐步补充材料
4. Agent 调用对应 tools / skills 完成导入
5. 系统生成 `Project Space` 和初版 `System Image`

版本创建示例：

1. 版本负责人输入“为项目 A 创建 2026Q2 版本”
2. Agent 询问版本关联的 Git 分支、US 集合和参与者
3. 用户确认后，系统创建 `Version Branch`
4. Agent 自动总结版本初始风险，并建议后续 US 分配方式

个人工作示例：

1. 质量参与者输入“开始处理 US-123”
2. Agent 自动加载该 US 的上下文、系统画像关联和历史测试资产
3. Agent 先完成 US 质量分析，再逐步输出测试场景、测试范围、测试计划、测试用例和脚本建议
4. 用户继续通过对话触发执行、复核结果、生成总结和变更文档

进度查询示例：

1. 用户输入“帮我查看当前的测试进度”
2. Agent 识别为查询类工具调用
3. 系统调用进度查询工具，读取版本、US、Run 和审批状态
4. Agent 以结构化摘要 + 对话说明的形式返回当前测试进度、阻塞项和建议下一步

## 6. 端到端用户旅程

| 触发者 | 质量参与者、质量负责人 |

## 7. 能力目录

### 7.1 项目空间能力

- 创建和管理项目空间
- 导入 Git 仓库、US 文档、UX 图、OpenAPI、历史测试资产
- 初始化系统画像
- 查看系统画像的模块、页面、接口、依赖和历史测试关系
- 管理正式系统画像分支
- 配置项目级策略、角色和权限

### 7.2 版本空间能力

- 创建版本分支
- 导入版本级 US、Git 分支、版本说明和变更文档
- 把参与者加入当前版本
- 为参与者分配指定 US
- 查看版本级质量进度、US 闭环状态和版本风险
- 汇总版本放行准备度
- 发起版本收口和系统画像回基线

### 7.3 个人工作空间能力

- 通过对话方式启动和推进指定 US 的质量闭环
- 自动关联当前 US 与系统画像中的模块、页面、接口和历史资产
- 生成测试场景、测试范围、测试计划、测试用例
- 生成自动化脚本和性能测试脚本
- 生成变更文档和变更方案
- 发起执行、总结结果、输出问题说明和回归建议

### 7.4 共享执行与治理能力

- 统一 `Run` 和 `Evidence` 模型
- 统一审计和审批
- 统一版本风险评估
- 统一系统画像分支管理和合并
- 统一基线回写与知识沉淀

### 7.5 工具原生能力

- `Project Tools`
  - 创建项目、导入 Git、导入 US 文档、导入 UX、初始化系统画像、查看项目状态
- `Version Tools`
  - 创建版本分支、导入版本 US、关联 Git 分支、分配参与者、查看版本质量进度
- `US / Task Tools`
  - 启动 US 质量闭环、生成测试场景、测试范围、测试计划、测试用例、变更文档、总结结果
- `Execution Tools`
  - 生成自动化脚本、触发执行、查看执行进度、回放、失败归因、修复建议
- `Governance Tools`
  - 发起审批、合并冲突、提交放行、写回基线、查看审批状态
- `Query / Insight Tools`
  - 查看当前测试进度、查看版本风险、查看系统画像、查看 US 状态、查看未闭环项

## 8. Agent 与确定性质量闭环的结合方式

### 8.1 基本原则

不是所有环节都应该让 Agent 自主决定。  
Nasus 要做的是“Agent 负责理解、规划、选用工具、协同和总结；系统负责治理、执行、审批和正式落库”。

### 8.2 适合对话驱动的环节

| 环节 | 为什么适合 Agent |
| --- | --- |
| 项目创建与材料导入引导 | 输入不完整，适合通过追问逐步收集 |
| 版本创建与 US 导入 | 需要对变更范围做解释和建议 |
| US 质量分析 | 需要结合系统画像做上下文理解 |
| 测试场景、测试范围、测试计划、测试用例生成 | 需要结合历史知识做多步推理 |
| 执行后结果总结 | 需要把大量证据压缩成可消费结论 |
| 版本风险解释 | 需要把多个 US 状态整合成管理视角说明 |
| 再基线建议 | 需要判断哪些新增知识值得沉淀 |

### 8.3 必须保持确定性的环节

| 环节 | 为什么必须确定性 |
| --- | --- |
| 原料导入与对象落库 | 需要稳定的数据契约 |
| `Run` 创建与执行通道选择 | 需要可追踪、可审计 |
| 脚本执行 | 需要可回放和一致结果 |
| 审批与放行 | 需要正式治理流 |
| 系统画像分支合并 | 需要明确来源、差异和审批结果 |
| 证据保留 | 需要 append-only |

### 8.4 产品级分层建议

| 层 | 职责 |
| --- | --- |
| `Conversation Agent Layer` | 面向用户对话、理解意图、规划步骤、组织协作，并把输入解析成工具调用计划 |
| `Tool Contract Layer` | 把所有业务动作封装成可被主 Agent 和 UI 统一调用的正式工具 |
| `Skill / Worker Layer` | 作为工具背后的能力组件和执行单元，负责具体分析、生成和归因 |
| `Deterministic Execution Layer` | 承载脚本执行与证据留存 |
| `Governance Layer` | 承载审批、放行、分支管理、基线回写、审计 |
| `Knowledge Layer` | 承载系统画像、版本分支、US 质量资产和历史证据 |

## 9. Agent 交互与能力边界

### 9.1 Agent 形态

- 采用 `Central Agent`
- Tool 是产品级动作抽象，Skill 默认作为工具背后的内部能力组件，并以中心侧统一编排为准
- Web 显式展示可调用的工具，并允许在高级视图中展示工具背后的 Skill 组成
- 当前阶段由中心侧统一推理并写入 `AgentDecision(status=provisional)`
- 正式结论必须由 `Merge/Score + Approval Control` 形成 `MergedResolution`

### 9.2 Agent 可以做的事

- 通过对话收集信息
- 规划多步工作流
- 调用 tools，并在工具内部编排对应的 skills / workers
- 生成结构化质量资产草案
- 总结结果
- 提出放行建议
- 提出再基线建议

### 9.3 Agent 不能直接做的事

- 不能绕过审批直接写正式放行结论
- 不能绕过治理直接把版本知识写回正式系统画像
- 不能绕过执行器直接认定执行成功
- 不能绕过权限直接执行高风险动作

### 9.4 Tool 原生边界

- 所有业务动作默认都应先被定义成工具，而不是先做成只存在于界面上的按钮流程。
- 高风险工具允许被 Agent 发起，但默认进入 `waiting_confirmation` 或 `waiting_approval`。
- UI 动作、批量动作、主会话动作和外部 API 动作，本质上都应能回溯到同一类 `ToolInvocation`。
- 读查询可以通过 read API 实现，但核心写操作和工作流推进必须能被主 Agent 直接触发。

## 10. 默认规则

| 规则项 | 默认值 |
| --- | --- |
| 主入口 | `Web Portal` |
| 主交互方式 | 对话优先 |
| 第一操作入口 | `Conversation Session` |
| 主要工作组织方式 | `Project Space -> Version Space -> Personal Workspace` |
| 写操作 canonical entry | `ToolInvocation` |
| 正式基线源头 | `Official System Image Branch` |
| 版本工作载体 | `Version Branch` |
| 质量工作粒度 | `US Work Item` |
| 对话输出默认形态 | 优先落为结构化对象，不止停留在文本 |
| 页面动作语义 | 同一工具体系的可视化封装 |
| 执行记录 | 统一为 canonical `Run`，必须带 `execution_channel` |
| 决策记录 | 中心侧先产出 `AgentDecision(status=provisional)` |
| 冲突状态 | 统一进入 `pending_merge` |
| 正式结论对象 | `MergedResolution` |
| 高风险工具动作 | 必须经过权限、策略、审计和必要确认/审批 |
| 系统画像回基线 | 版本上线并审批通过后才能执行 |

## 11. 明确不做的事

- 不做通用代码生成器
- 不做纯文本聊天工具
- 不把对话中的临时结论直接视为正式系统知识
- 不把版本质量闭环简化成单纯的测试用例生成器
- 不让执行、审批、基线合并脱离审计链

## 12. 可借鉴的产品与模式

Nasus 不是现成产品的简单复制，但可借鉴以下模式：

| 产品 / 模式 | 适合借鉴的点 | 不应照搬的点 |
| --- | --- | --- |
| Google AI Studio | 对话工作台形态、主画布 + 侧边上下文的交互方式 | 不能停留在通用 prompt playground |
| qTest / 类 Test Management 平台 | 需求到测试资产的追踪关系、版本质量汇总 | 不能只做手工测试管理 |
| mabl / Momentic / QA 自动化产品 | AI 辅助脚本生成、执行反馈回路 | 不能把产品重心缩成自动化执行器 |
| Plutora / Release Management 平台 | 版本风险、放行门禁、审批治理 | 不能变成纯流程审批系统 |
| Agent Workbench 类产品 | 对话式 Agent 工作台、工具编排和治理 | 不能变成脱离质量对象模型的通用 Agent 平台 |

## 13. 与现有架构文档的关系

- 本说明书先定义产品定位、空间模型、用户旅程和能力边界。
- 架构文档和前后端方案文档应在下一轮对齐到以下主线：
  - 以 `Project Space / Version Space / Personal Workspace` 为产品组织方式
  - 以 `System Image / Version Branch / US Work Item / Quality Asset Pack` 为核心对象
  - 以“对话优先 + 工具原生 + 结构化落库 + 确定性执行 + 正式治理流”为实现原则

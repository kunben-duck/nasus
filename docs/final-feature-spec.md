## 2. 产品定位

### 2.1 一句话定位

Nasus 是一个面向存量系统增量迭代的 AI 原生质量闭环平台。  
它通过“项目空间 + 版本空间 + 个人工作空间 + 对话式 Agent”把系统画像、US 质量分析、测试资产生成、自动化执行、版本风险评估和上线后再基线化串成一个连续闭环。

### 2.2 产品要解决的问题

在存量系统中，版本迭代通常同时存在以下问题：

- 系统知识分散在 Git、US、文档、UX 图、历史测试资产里，团队无法形成稳定系统画像。
- 版本新增 US 后，质量工作往往只停留在临时测试任务，没有沉淀为后续可复用知识。
- 测试场景、范围、计划、用例、自动化脚本、性能脚本、变更文档和上线判断是分散完成的，缺少统一质量闭环。
- AI 可以提高产出速度，但如果没有对象模型、审批和证据链，很容易变成不可追溯的“会话式输出”。

Nasus 的目标不是做通用聊天工具，而是把 AI 变成版本质量工作的正式参与者。

### 2.3 核心产品原则

- **US 中心闭环**：质量工作围绕每个 US 展开，而不是停留在泛化任务列表。
- **系统画像是长期资产**：系统画像不是一次性导入结果，而是可基线化、可分支、可合并的长期知识对象。
- **对话优先，不等于无结构**：用户主要通过对话驱动 Agent 完成工作，但所有关键输出都必须落成结构化对象。
- **Agent 负责规划，系统负责治理**：Agent 可以自主规划和调用 tools/skills，但正式结论、审批、基线写回仍由治理流控制。
- **版本分支像 Git 一样工作**：版本工作在系统画像分支上展开，上线后再把新知识合并回正式系统画像。
- **执行必须确定性**：测试执行、证据留存、审批和基线合并都必须具备确定性、可审计和可回放。

## 3. 目标用户、角色与空间模型

### 3.1 核心角色

| 角色 | 核心职责 | 默认关注空间 |
| --- | --- | --- |
| 平台管理员 | 创建项目空间、导入存量系统知识、初始化系统画像、配置权限与策略、管理正式基线 | `Project Space` |
| 版本负责人 | 创建版本分支、导入版本级 US 和 Git 分支、分配参与者、推进版本质量闭环 | `Version Space` |
| 质量负责人 | 审核 US 质量分析、确认测试范围和测试计划、复核执行结果、推动放行结论 | `Version Space` |
| 质量参与者 | 接收指定 US，完成测试场景、范围、计划、用例、脚本、执行和结果总结 | `Personal Workspace` |
| 审批者 / 发布负责人 | 审批知识晋级、审批版本放行、批准系统画像回基线 | `Version Space` `Project Space` |

说明：

- `Desktop Client` 是运行端和执行入口，不是独立业务角色。
- 平台管理员、版本负责人、质量负责人、质量参与者都可能在特定场景下通过 `Desktop Client` 执行本地动作。

### 3.2 空间模型

| 空间 | 定位 | 主要对象 | 典型动作 |
| --- | --- | --- | --- |
| `Project Space` | 项目级长期质量空间 | Git 仓库、US 文档、UX 图、系统画像、正式系统基线、参与者、策略 | 创建项目、导入原料、初始化系统画像、查看全局知识、管理基线分支 |
| `Version Space` | 版本级质量闭环空间 | 版本分支、版本级 US、开发分支、版本风险、版本质量资产、放行结论 | 创建版本、导入版本输入、分配 US、监控质量进度、审批放行 |
| `Personal Workspace` | 个人执行与对话工作空间 | 分配到个人的 US、质量任务、质量资产、执行结果、会话 | 通过对话完成分析、生成资产、执行脚本、总结结果 |
| `Desktop Client` | 本地执行和本地权限空间 | 本地会话、本地产物、本地能力授权、本地执行队列 | 执行本地动作、上传本地证据、接受远程任务、离线补传 |

### 3.3 入口默认值

| 入口 | 最终定位 |
| --- | --- |
| `Web Portal` | 默认正式工作台入口，承接项目空间、版本空间、组织级协作和审批 |
| `Desktop Client` | 默认个人执行入口，承接本地能力和本地执行 |
| `CLI / API` | 辅助入口，服务于集成、批处理和自动化 |
| `Assistant` | 增强入口，复用同一套对象模型和 Agent 能力，但不高于 `Web Portal` |

## 4. 核心对象与分支模型

### 4.1 核心对象

| 对象 | 定义 | 默认归属 |
| --- | --- | --- |
| `Project Space` | 一个存量系统的质量主空间，承接长期知识、参与者和治理规则 | 项目级 |
| `System Image` | 从 Git、US、UX、OpenAPI、历史测试资产中抽取出的系统画像 | 项目级长期对象 |
| `Official System Image Branch` | 正式系统画像分支，是后续版本分支的源头 | 项目级正式基线 |
| `Version Branch` | 某次版本从正式系统画像分出的工作分支，承接版本增量知识和风险 | 版本级 |
| `US Work Item` | 版本中的一个 US 单元，绑定需求描述、责任人、相关系统对象和质量闭环状态 | 版本级 |
| `Quality Task` | 围绕某个 US 产生的一次具体质量任务或子任务 | US 级 |
| `Quality Asset Pack` | 围绕 US 形成的一组质量资产，包括测试场景、范围、计划、用例、自动化脚本、性能脚本、变更文档和变更方案 | US 级 |
| `Run` | 一次正式执行实例的 canonical 对象，必须带 `execution_channel=web_runner|desktop_local` | 执行层正式对象 |
| `Evidence` | 执行结果、截图、日志、trace、归因、总结等证据对象 | 证据层 |
| `AgentDecision` | 中心端或桌面端产出的候选分析、归因、修复、放行或知识判断，状态为 `provisional / merged / approved / rejected` | 候选决策层 |
| `MergedResolution` | 由 `Merge/Score + Approval Control` 汇总形成的正式任务结论、正式放行建议或正式知识结论 | 正式治理层 |
| `Conversation Session` | 用户在项目空间、版本空间或个人工作空间中的一次对话工作会话 | 会话层 |

### 4.2 术语映射

为了兼容现有架构文档中的命名，产品术语与系统术语做如下映射：

| 产品术语 | 系统术语 |
| --- | --- |
| `System Image` | `Context Objects + Baseline` |
| `Official System Image Branch` | `Official Baseline` |
| `Version Branch` | `Version Working Baseline` |
| `Conversation Session` | `Session` |
| `US 质量任务上下文` | `Task Context Workspace` |
| `US 质量画像` | `Quality Assurance Profile` |

### 4.3 分支与合并规则

- `Official System Image Branch` 是所有版本分支的默认源头。
- 每个 `Version Branch` 必须从当前正式系统画像分支创建。
- 版本中新增的特性文档、测试场景、测试用例、Git 最新改动、执行结果和确认后的知识，先沉淀在版本分支内。
- 版本上线完成并审批通过后，版本分支中的新增知识才能合并回正式系统画像分支。
- 不同版本可以并行从同一个正式系统画像分支开出不同工作分支。
- 分支合并必须保留来源、证据、审批和差异说明。

## 5. 产品交互模型

### 5.1 对话优先的工作方式

Nasus 的主交互方式不是多页面表单流，而是“带结构化上下文的对话工作台”。

每个空间都以一个主对话界面为中心，参考 AI Studio 的工作方式：

- 左侧是空间导航和对象切换。
- 中间是主对话画布，用于持续与 Agent 协作。
- 右侧是结构化上下文面板，展示当前项目、版本、US、系统画像、质量资产、执行结果和审批状态。
- 底部是主输入框，用户通过自然语言驱动任务闭环。

### 5.2 对话不是纯聊天

对话的作用是驱动工作闭环，而不是输出一次性文本。

每次对话都应尽量映射到以下结构化动作之一：

- 创建项目空间
- 导入系统原料
- 初始化系统画像
- 创建版本分支
- 导入版本级 US / Git 分支
- 分配 US
- 启动 US 质量分析
- 生成质量资产
- 触发执行
- 总结结果
- 发起放行审批
- 发起系统画像再基线化

### 5.3 对话交互示例

项目创建示例：

1. 管理员输入“我想创建一个新的项目”
2. Agent 回复“我可以为你创建项目，请提供 Git 仓库地址、US 文档、UX 图或 OpenAPI”
3. 管理员逐步补充材料
4. Agent 调用对应 tools / skills 完成导入
5. 系统生成 `Project Space` 和初版 `System Image`

版本创建示例：

1. 版本负责人输入“为项目 A 创建 2026Q2 版本”
2. Agent 询问版本关联的 Git 分支、US 集合和参与者
3. 用户确认后，系统创建 `Version Branch`
4. Agent 自动总结版本初始风险，并建议后续 US 分配方式

个人工作示例：

1. 质量参与者输入“开始处理 US-123”
2. Agent 自动加载该 US 的上下文、系统画像关联和历史测试资产
3. Agent 先完成 US 质量分析，再逐步输出测试场景、测试范围、测试计划、测试用例和脚本建议
4. 用户继续通过对话触发执行、复核结果、生成总结和变更文档

## 6. 端到端用户旅程

### 6.1 项目初始化

| 项目 | 内容 |
| --- | --- |
| 触发者 | 平台管理员 |
| 入口空间 | `Project Space` |
| 核心动作 | 创建项目空间、导入 Git 仓库、US 文档、UX 图、OpenAPI、历史测试资产 |
| Agent 作用 | 对话式收集缺失输入、决定导入顺序、建议初始化范围 |
| 关键产物 | `System Image`、`Official System Image Branch` |
| 结果 | 项目从“无质量资产”进入“有系统画像和正式基线”的可协作状态 |

### 6.2 版本启动

| 项目 | 内容 |
| --- | --- |
| 触发者 | 版本负责人 |
| 入口空间 | `Version Space` |
| 核心动作 | 创建版本分支、导入版本级 US、导入开发分支、加入参与者 |
| Agent 作用 | 识别版本增量范围、构建版本初始风险、建议 US 拆分和分配 |
| 关键产物 | `Version Branch`、版本风险视图、US 列表 |
| 结果 | 版本从“输入材料集合”进入“可分配、可追踪”的质量工作状态 |

### 6.3 US 质量闭环

| 项目 | 内容 |
| --- | --- |
| 触发者 | 质量参与者、质量负责人 |
| 入口空间 | `Personal Workspace` |
| 核心动作 | 围绕指定 US 开展质量分析，生成测试场景、测试范围、测试计划、测试用例、自动化脚本、性能脚本、变更文档和变更方案 |
| Agent 作用 | 关联系统画像、主动规划步骤、调用 skills / tools、生成结构化质量资产 |
| 关键产物 | `Quality Asset Pack` |
| 结果 | 每个 US 都形成可审阅、可执行、可沉淀的质量资产集 |

### 6.4 执行与结果总结

| 项目 | 内容 |
| --- | --- |
| 触发者 | 质量参与者、质量负责人，以及在桌面端运行任务的相关角色 |
| 入口空间 | `Personal Workspace` `Desktop Client` |
| 核心动作 | 触发自动化脚本执行、性能脚本执行、本地动作执行，收集证据并总结结果 |
| Agent 作用 | 决定调用哪类执行能力、总结执行结果、归纳失败原因、给出下一步建议 |
| 关键产物 | `Run`、`Evidence`、执行总结、失败归因、修复建议 |
| 结果 | US 级质量资产从“设计完成”进入“执行完成且有证据支撑” |

### 6.5 版本放行

| 项目 | 内容 |
| --- | --- |
| 触发者 | 版本负责人、质量负责人、审批者 |
| 入口空间 | `Version Space` |
| 核心动作 | 汇总版本内所有 US 的质量资产和执行结果，评估版本风险与上线准备度 |
| Agent 作用 | 汇总版本级风险、识别未闭环项、生成放行建议和版本总结 |
| 关键产物 | 版本风险评估、放行建议、审批记录 |
| 结果 | 版本从“质量执行中”进入“可上线 / 阻断 / 待补证”的正式状态 |

### 6.6 上线后再基线化

| 项目 | 内容 |
| --- | --- |
| 触发者 | 平台管理员、审批者、版本负责人 |
| 入口空间 | `Project Space` `Version Space` |
| 核心动作 | 将版本中的新增特性文档、测试场景、测试用例、Git 最新改动和确认后的知识重新写入系统画像，并把版本分支合并回正式系统画像分支 |
| Agent 作用 | 识别本次版本中哪些内容值得纳入长期系统画像，并生成再基线建议 |
| 关键产物 | 更新后的 `Official System Image Branch` |
| 结果 | 项目长期知识持续演进，下一版本可以直接复用这次闭环沉淀 |

## 7. 能力目录

### 7.1 项目空间能力

- 创建和管理项目空间
- 导入 Git 仓库、US 文档、UX 图、OpenAPI、历史测试资产
- 初始化系统画像
- 查看系统画像的模块、页面、接口、依赖和历史测试关系
- 管理正式系统画像分支
- 配置项目级策略、角色和权限

### 7.2 版本空间能力

- 创建版本分支
- 导入版本级 US、Git 分支、版本说明和变更文档
- 把参与者加入当前版本
- 为参与者分配指定 US
- 查看版本级质量进度、US 闭环状态和版本风险
- 汇总版本放行准备度
- 发起版本收口和系统画像回基线

### 7.3 个人工作空间能力

- 通过对话方式启动和推进指定 US 的质量闭环
- 自动关联当前 US 与系统画像中的模块、页面、接口和历史资产
- 生成测试场景、测试范围、测试计划、测试用例
- 生成自动化脚本和性能测试脚本
- 生成变更文档和变更方案
- 发起执行、总结结果、输出问题说明和回归建议

### 7.4 共享执行与治理能力

- 统一 `Run` 和 `Evidence` 模型
- 统一审计和审批
- 统一版本风险评估
- 统一系统画像分支管理和合并
- 统一基线回写与知识沉淀

## 8. Agent 与确定性质量闭环的结合方式

### 8.1 基本原则

不是所有环节都应该让 Agent 自主决定。  
Nasus 要做的是“Agent 负责理解、规划、协同和总结；系统负责治理、执行、审批和正式落库”。

### 8.2 适合对话驱动的环节

| 环节 | 为什么适合 Agent |
| --- | --- |
| 项目创建与材料导入引导 | 输入不完整，适合通过追问逐步收集 |
| 版本创建与 US 导入 | 需要对变更范围做解释和建议 |
| US 质量分析 | 需要结合系统画像做上下文理解 |
| 测试场景、测试范围、测试计划、测试用例生成 | 需要结合历史知识做多步推理 |
| 执行后结果总结 | 需要把大量证据压缩成可消费结论 |
| 版本风险解释 | 需要把多个 US 状态整合成管理视角说明 |
| 再基线建议 | 需要判断哪些新增知识值得沉淀 |

### 8.3 必须保持确定性的环节

| 环节 | 为什么必须确定性 |
| --- | --- |
| 原料导入与对象落库 | 需要稳定的数据契约 |
| `Run` 创建与执行通道选择 | 需要可追踪、可审计 |
| 脚本执行 | 需要可回放和一致结果 |
| 审批与放行 | 需要正式治理流 |
| 系统画像分支合并 | 需要明确来源、差异和审批结果 |
| 证据保留 | 需要 append-only |

### 8.4 产品级分层建议

| 层 | 职责 |
| --- | --- |
| `Conversation Agent Layer` | 面向用户对话、理解意图、规划步骤、组织协作 |
| `Skill / Tool Layer` | 把常用质量能力封装成可调用单元 |
| `Deterministic Execution Layer` | 承载脚本执行、桌面动作、本地动作、证据留存 |
| `Governance Layer` | 承载审批、放行、分支管理、基线回写、审计 |
| `Knowledge Layer` | 承载系统画像、版本分支、US 质量资产和历史证据 |

## 9. Agent 交互与能力边界

### 9.1 Agent 形态

- 采用 `Central Agent + 完整 Edge Agent`
- Skill 默认 `中心为主、少量本地下沉`
- Web 和 Desktop 都显式展示 Skill
- 双端都可以独立推理
- 双端都只能先写入 `AgentDecision(status=provisional)`
- 正式结论必须由 `Merge/Score + Approval Control` 形成 `MergedResolution`

### 9.2 Agent 可以做的事

- 通过对话收集信息
- 规划多步工作流
- 调用 tools / skills
- 生成结构化质量资产草案
- 总结结果
- 提出放行建议
- 提出再基线建议

### 9.3 Agent 不能直接做的事

- 不能绕过审批直接写正式放行结论
- 不能绕过治理直接把版本知识写回正式系统画像
- 不能绕过执行器直接认定执行成功
- 不能绕过权限直接执行高风险本地动作

## 10. 默认规则

| 规则项 | 默认值 |
| --- | --- |
| 主入口 | `Web Portal` |
| 本地执行入口 | `Desktop Client` |
| 主交互方式 | 对话优先 |
| 主要工作组织方式 | `Project Space -> Version Space -> Personal Workspace` |
| 正式基线源头 | `Official System Image Branch` |
| 版本工作载体 | `Version Branch` |
| 质量工作粒度 | `US Work Item` |
| 对话输出默认形态 | 优先落为结构化对象，不止停留在文本 |
| 执行记录 | 统一为 canonical `Run`，必须带 `execution_channel` |
| 决策记录 | 双端先产出 `AgentDecision(status=provisional)` |
| 冲突状态 | 统一进入 `pending_merge` |
| 正式结论对象 | `MergedResolution` |
| 高风险动作 | 必须经过权限、策略、审计和必要确认 |
| 系统画像回基线 | 版本上线并审批通过后才能执行 |

## 11. 明确不做的事

- 不做通用代码生成器
- 不做纯文本聊天工具
- 不把对话中的临时结论直接视为正式系统知识
- 不把版本质量闭环简化成单纯的测试用例生成器
- 不让执行、审批、基线合并脱离审计链

## 12. 可借鉴的产品与模式

Nasus 不是现成产品的简单复制，但可借鉴以下模式：

| 产品 / 模式 | 适合借鉴的点 | 不应照搬的点 |
| --- | --- | --- |
| Google AI Studio | 对话工作台形态、主画布 + 侧边上下文的交互方式 | 不能停留在通用 prompt playground |
| qTest / 类 Test Management 平台 | 需求到测试资产的追踪关系、版本质量汇总 | 不能只做手工测试管理 |
| mabl / Momentic / QA 自动化产品 | AI 辅助脚本生成、执行反馈回路 | 不能把产品重心缩成自动化执行器 |
| Plutora / Release Management 平台 | 版本风险、放行门禁、审批治理 | 不能变成纯流程审批系统 |
| Agent Workbench 类产品 | 对话式 Agent 工作台、工具编排和治理 | 不能变成脱离质量对象模型的通用 Agent 平台 |

## 13. 与现有架构文档的关系

- 本说明书先定义产品定位、空间模型、用户旅程和能力边界。
- 架构文档和前后端方案文档应在下一轮对齐到以下主线：
  - 以 `Project Space / Version Space / Personal Workspace` 为产品组织方式
  - 以 `System Image / Version Branch / US Work Item / Quality Asset Pack` 为核心对象
  - 以“对话优先 + 结构化落库 + 确定性执行 + 正式治理流”为实现原则

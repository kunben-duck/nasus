## 1. 当前结论与业务背景

Nasus 的项目目标是：在 AI Coding 带来的连续、高频代码变更下，通过持续演进的系统画像维护系统认知，识别集成影响，复用和补充必要测试，并依据目标版本的有效执行证据支撑发布判断。核心方法也适用于人工产生的代码变更。

需要解决的技术问题包括：

- 代码、需求和测试材料各自变化，旧系统认知及跨源关系不能直接用于新版本。
- 静态调用关系、文档引用及名称相似度不足以证明“实现了需求”或“验证了条件”。
- 检索截取和上下文预算可能使必验条件消失；生成结果可能改写预期或遗漏联合条件。
- 新增文件和空召回可能未出现在旧命中证据中，单看命中材料容易遗漏影响。
- 历史资产可以复用，但旧版本通过记录不能直接支撑新版本放行。
- 重新理解整个系统、重复生成资产和人工核对版本，会增加变更反馈成本。

当前讨论收敛为两个候选技术保护主题：

| 主题 | 具体技术问题 | 核心处理对象 |
| --- | --- | --- |
| **系统画像的有效构建** | 跨源关系依据什么成立，重复生成时如何尊重历史判断，端点变化后如何重新判断适用性 | 来源修订、实体身份、双端证据、关系主张、审阅决定及新画像成员之间的约束 |
| **系统画像的有效使用** | 如何使完整的验证责任在检索、分包和生成过程中保持，如何防止过期依据被当作当前通过 | 独立验收判据、完整义务集合、分包归属、用例或缺口、目标证据及当前适用性之间的约束 |

这两项是有实现基础的候选组合。多源建图、动态图谱、增量更新、证据校验、人工审批、RAG 和测试反馈均已有公开基础，不能据其在本项目中形成闭环就推导出创造性。当前既不能断言项目完全没有创新，也没有充分依据认定已经形成可授权的核心发明点。

项目价值、工程实现和专利创造性是不同判断。解决真实问题并实现复杂系统，不自动满足专利创造性要求；现有技术中出现若干相同组成部分，也不能单独否定一个具体组合。需比较完整技术方案及其实际作用关系。[R10](#r10)

## 3. 当前画像的技术形态与存储

系统画像是带来源证据、实体关系、修订和适用状态的知识快照。当前技术主体为“关系型数据管理＋不可变工件归档＋图关系表达＋检索投影”。

| 层次 | 当前技术 | 作用及边界 |
| --- | --- | --- |
| 来源采集 | Git、对象存储及受目录约束的本地来源；文件清单和内容哈希 | 输入分代码、需求文档、测试资产；URI 被允许不代表已实现对应远程采集器 |
| 代码结构 | 默认 Tree-sitter；可配置 CodeGraph 或 codebase-memory | 提取实体及部分结构关系；外部代码图的代码默认配置为 disabled，不代表部署进程一定采用该默认值 |
| 文档结构 | Markdown/TXT/CSV 显式格式及字段解析；Python 测试使用 AST | 识别需求、AC、规则、用例、步骤和预期；不是任意文档的通用语义理解 |
| 主数据 | SQLAlchemy 实体、关系、修订和成员表；生产方案 PostgreSQL，未配置数据库时默认 SQLite | 保存身份、关系、证据关联、审阅与发布状态；未核查的部署环境不能直接描述为已使用某种数据库 |
| 原始材料与工件 | 对象存储中的原文、JSON 工件及内容摘要 | 记录来源快照、画像、模型响应及历史产物，读取时核验内容 |
| 检索索引 | PostgreSQL FTS、pgvector、候选排序及降级记录 | 用于召回和排序；索引或相似度不是正式业务事实源 |
| 语义关联 | 固定端点及输入的模型调用、结构化校验、独立审阅 | 生成受证据约束的关系候选，不自动证明关系业务语义正确 |
| 构建编排 | AgentGoal、工具运行时、分阶段执行及任务生命周期 | 已有结构构建到有限调查的实际链路；完整自主语义补全和后台维护尚未贯通 |

图关系可以用关系表存储，专用图数据库也可以承担图查询投影。当前 Nasus 主数据不以专用图数据库为基础。替换数据库、引入向量库或使用 AST，本身不作为核心创新点。

基础代码分析支持 Python、JavaScript、TypeScript/TSX、Java、Go，提取文件模块、类、接口、枚举、函数/方法、导入依赖及部分 HTTP 路由。调用关系部分依靠名称匹配，目标不唯一时保留未解析状态。基础展示投影主要归并为包含和依赖，不能描述为全项目完整运行时调用图或业务因果图。

核心对象分工如下：

| 对象 | 决定性字段或作用 |
| --- | --- |
| SourceBinding / SourceRevision | 来源身份、外部修订、文件清单、内容摘要和采集状态 |
| SourceManifest | 本轮完整来源组合及各来源状态，固定跨仓库/文档输入 |
| 实体与实体修订 | 稳定身份、类型、来源修订及定位；身份有歧义时不伪造正式对象 |
| 证据 | 原始文件或字段、定位、内容及摘要 |
| 关系主张与审阅决定 | 固定端点、端点修订、关系类型、证据、模型评估与审阅历史 |
| ImageRevision | 固定对象、关系、证据成员、父修订及工件摘要 |
| Publication | 独立发布决定和当前画像指针，不修改历史画像内容 |
| ContextPack / Scope / Obligation | 下游用途输入、范围及完整验证义务，不等于执行结果 |

## 4. 系统画像如何构建有效的多源关系

### 4.1 固定来源，分开结构事实与规范预期

采集形成不可变来源修订，SourceManifest 固定本轮全部选定来源及状态。构建读取归档来源，避免工作区继续变化导致同一轮混用内容。选中的代码来源必须完成采集；缺少需求或历史测试可以继续结构构建，但必须保留相应能力缺口。

代码解析形成观察事实，需求与业务规则提供预期候选，历史测试提供步骤和断言候选。代码现有行为不能自动成为正确业务预期；测试源码存在也不代表测试运行过。

### 4.2 建立能核对身份和修订的端点

代码实体通过规范符号键注册，绑定实体修订和来源修订。文档按显式编号和字段形成需求、验收条件、业务规则、用例或文档对象，保留原文定位。身份含糊、无法注册的代码观察保留在分析报告中。

正式冻结画像禁用旧版标签相似度跨源连边和合成 Core 节点。名称相似可以用于发现候选，不能直接生成“实现”或“断言”事实。

### 4.3 按关系类型要求不同的证据

| 关系 | 当前含义 | 不能直接推出的结论 |
| --- | --- | --- |
| 结构包含、依赖 | 解析器或已验证代码分析提供的结构观察 | 业务需求已实现、全部动态依赖已识别 |
| references | 文档或测试明确引用某个需求标识，目标身份可解析 | 被引用需求已实现或已被测试覆盖 |
| implements | 代码与 AC/规则之间的实现关系候选，提供两端证据并审阅 | 运行行为一定正确 |
| asserts | 用例与 AC 之间的断言关系候选，必须引用已有预期结果字段 | 该用例已执行或目标版本已通过 |

模型只评估选定画像内的固定端点。程序检查输入摘要、两端修订、引文范围、原文和摘要，区分 supports、contradicts、unrelated、unknown。未知必须说明缺失信息；涉及断言的支持判断不得生成一个新的预期来替代原字段。

两端引文和摘要一致能够核对出处及输入一致性，不能证明模型对业务关系的判断正确。独立审阅决定同样不能替代运行事实。

### 4.4 保留关系主张及历史决定，约束再次生成

同一固定画像、端点修订和谓词确定关系主张身份 claim_id；单次模型调用对应 evaluation_id。重新调用模型不重置同一主张的审阅历史。

适用性处理如下：

| 变化情况 | 当前处理 |
| --- | --- |
| 同一端点身份及修订，历史决定为 reject | 限制该关系进入未审阅候选和模型再评估；不能借模型重跑绕过历史决定 |
| 同一身份，但端点或来源修订变化 | 标记需重新验证和审阅，不自动继承旧接受，也不永久沿用旧否定 |
| 身份变化或无法明确比较 | 先解决身份，不能直接转移历史判断 |
| 同修订曾接受或暂缓 | 历史判断可作为依据，不能自动视为新画像的批准 |

对召回范围内的完整候选排序，先执行上述适用性筛选，再截取候选。筛选针对特定关系，不是永久删除或拉黑整个测试资产。

### 4.5 冻结与发布

审阅后冻结新画像时，重新核验来源证据、父画像成员和当前决定，保存新的画像工件。画像可包含接受、拒绝、暂缓的判断记录，不能把所有记录都称为成立的业务边。

画像发布单独固定候选、来源、政策及预期当前头，提交前重验并原子推进指针。知识画像发布、Agent 构建完成、测试执行授权和软件发布准入分别判断。

## 5. 新文档或代码如何形成下一版画像

当前已有显式来源刷新、双修订差异、成员差异、关系适用性、有界派生影响及失效处理。处理过程及边界如下：

1. **刷新来源。** 固定旧来源清单，仅重新采集选定来源；新清单仍记录完整来源组合及状态，不覆盖正在验证的快照。
2. **比较双修订。** 同一来源绑定的两个修订按文件和摘要比较。只有采集范围完整且可比较，才能确认真实新增或删除；读取失败、排除项或范围变化保留未决状态。
3. **比较画像成员。** 对两个冻结画像按注册实体身份识别成员变化。成员消失不等于源文件删除，重命名候选也不自动证明身份继承。
4. **重评关系。** 端点及证据变化后，历史接受和否定按适用性规则重新处理，不直接复制成新版本结论。
5. **判断派生影响。** 除已命中的证据，还考虑原查询范围；新增文件和空召回也可能改变原结论。当前对固定有界依赖图采用保守失效，历史内容保留，当前使用受限。
6. **形成新候选及下游输入。** 新画像经相应调查、审阅和发布后，再编译新的验证上下文。提交前复查依赖和当前头，处理分析期间发生的版本竞争。

已存在实际分阶段 Agent 链路，不能概括为“只有互不关联的工具”；但尚未完成“持续监听变化—精确局部重建—自动补证—语义复核—发布—补验”的后台全自动维护链。

设计中的入口驱动 BehaviorSpec、按用途反向检查“如何触发、期望什么、怎样观察、如何隔离”、以及缺口驱动调查具有可实施描述；完整字段级语义补全及完成判定尚未贯通。当前调查累计证据和画像摘要来识别进展，新摘要不等于语义缺口已减少。

当前不宣称全项目精确影响分析、全局最小重算或最小回归集。部分条件不明时扩大范围或阻断，是保守处理，不能包装为精确性成果。

## 6. 画像如何有效指导测试生成与验证

### 6.1 规范依据和支持材料分别编译

规范依据是独立批准的 AC、业务规则及可观察判据，决定必须验证什么。相关代码、结构关系和历史测试属于支持材料，帮助判断如何触发、观察及复用。

从固定画像枚举全部 AC 和业务规则，绑定原来源、文档和批准修订。Top-K 只筛选支持材料，不能决定保留哪些必验条件。当前尚无独立规则适用范围批准时，来源业务规则按全局规则处理。

完整性相对于固定画像中已提取、纳入范围且经过相应批准的条件。它不能证明原文所有隐含需求都已被识别，也不能证明输入规范本身没有错误。

### 6.2 编译完整义务并保留原判据

独立范围审阅后，AC、规则、风险、权限、状态转换、不变量及正反例形成义务行。每行保存身份、关联条件、证据、原判据及判据摘要。

当前 row_id 包含 scope_revision_id。固定输入内义务身份保持，不等于已经实现跨修订的同一业务义务识别。条件发生合法变更时，新版义务应重新确定；不能把所有历史义务永久累加。

### 6.3 完整分包与预算

- 单条 AC 和必要规则保持完整。
- 涉及多条条件的联合义务作为不可拆单元。
- 全局规则随包继承，共享义务具有唯一计数归属。
- 先容纳强制内容，再选择可选材料；不可拆单元超限时阻断，不截断强制条件。
- 上下文编译阶段采用 UTF-8 字节上界，实际模型调用另有 tokenizer、模型上下文容量和费用预算，不能将两种计量混用。

### 6.4 生成结果按义务逐项校验

程序验证每项义务至少对应一个用例映射或显式缺口；两者可以同时存在。模型不得通过省略义务缩小统计分母。

结果还需满足：引用来自实际输入；复用对象来自允许集合；每个用例继承全局规则；断言绑定真实步骤；原判据正文和摘要保持一致；用例与缺口身份不重复。

这些规则约束结构完整性、版本及引用，不自动证明测试步骤足以验证业务预期。生成后的覆盖状态仍是 planned，映射、用例、脚本审阅与执行分别处理。

### 6.5 执行证据及正式通过

已有 RunPlan 将脚本、用例、代码范围、构建、环境、数据和执行批次等输入绑定。执行前登记派发，执行后归档并核验原始观察。已派发但无可信结果时保留 unknown，不能直接记为通过或自动重发有副作用的动作。

资产复用不等于通过结论复用。本轮必测项需要适用于目标版本的证据；历史内容保留与当前适用性分别判断。

当前新执行链仍返回 `business_coverage_verified=false`、`canonical_execution_committed=false`，正式覆盖计数不会因原始观察自动增加。逐义务正式覆盖、目标证据接纳、软件发布准入和自动回流尚未全部贯通。完整方案要求关键失败、未知或缺证据阻断质量准入，操作审批不能覆盖这些缺口；这不能写成本轮已经验证的全链路事实。

运行观察可成为后续风险、缺陷和关联候选，经治理进入后续画像；它不能直接改写独立验收预期。

## 8. 两个主要候选创新点和技术保护机会

### 8.1 有效构建：版本化证据与关系审阅适用性共同约束关系演进

**候选名称：一种基于版本化证据和关系审阅适用性的多源系统画像构建与更新方法。**

核心组合为：固定来源与实体端点；按关系类型校验双端证据；分离关系主张和单次模型评估；以端点身份、端点修订和历史审阅决定控制再次召回及评估；提交前核验成员与决定，形成新的不可变画像修订。

| 具体技术限定 | 作用机制 | 当前状态 |
| --- | --- | --- |
| references、implements、asserts 使用不同接纳条件 | 阻止引用和相似性直接升级为实现或覆盖 | 已有组件 |
| 同一固定端点主张不随模型重跑重置 | 保留此前审阅约束，防止错误关系被反复生成 | 已有组件 |
| 同修订否定约束后续候选，修订变化要求重验证 | 同时防止旧错误重现和修正资产被永久排除 | 已有组件 |
| 筛选在候选截取之前执行，冻结时复查决定及证据 | 避免无效候选挤占名额及审阅期间变化被忽略 | 已有组件 |
| 用途缺口驱动调查、补证和完整完成判定 | 让画像补全围绕实际验证问题推进 | 部分实现及可实施设计，不能写成完整已交付能力 |

技术效果目标是减少错误关系再次生成、旧结论误用、修正关系错误排除和重复调查。程序校验只约束证据与状态一致性，不证明业务关系真值。

反方挑战：类型约束、来源定位、版本图谱、审批和失效都是常见机制。区别必须体现在它们如何共同控制同一关系的再生成与版本迁移，并形成可验证效果。当前属于较窄的候选保护方向，不能依靠模块叠加证明创造性。

### 8.2 有效使用：完整验证义务在检索、分包和生成校验间保持

**候选名称：一种基于完整验证义务编译的系统画像驱动测试生成及校验方法。**

核心组合为：从固定画像和独立批准的验收依据枚举完整条件；检索只选择辅助证据；将条件及范围项编译成固定义务；完整分包并继承全局规则；逐义务校验用例或显式缺口及原判据；分别记录计划覆盖和后续验证状态。

| 具体技术限定 | 作用机制 | 当前状态 |
| --- | --- | --- |
| 必验集合独立于 Top-K，判据独立于代码观察 | 避免检索遗漏及代码循环自证 | 已有组件和生成链路 |
| 完整条件、跨条件义务不可拆，全局规则继承 | 防止预算截断或分包丢失联合语义 | 已有组件和生成链路 |
| 唯一义务归属及完整集合核对 | 防止分包重复计数或静默缩小分母 | 已有组件和生成链路 |
| 每项义务 case/gap，断言保留原文及摘要 | 使遗漏显式化，阻止改写预期掩盖缺口 | 已有组件和生成链路 |
| 资产及执行记录绑定目标版本，历史与当前适用性分离 | 防止旧通过结论错误支撑新版本 | 已有分段基础，正式覆盖及发布闭环尚未贯通 |
| 跨修订识别同一业务义务、自动补验并恢复满足状态 | 将画像滚动更新转为有效迭代 | 尚缺完整义务沿革、支持关系和状态归约链路 |

相较于仅对已进入提示词的证据包做反查，该组合的完整性比较对象始终是固定义务集合。生成遗漏必须留下缺口，不能使义务从分母消失。其完整性仍受来源提取和范围正确性的限制。

反方挑战：完整约束清单、分包、schema、集合相等和引用校验都可能与常规 RAG 结合。需论证这些规则如何共同保持义务身份、判据与计数，不能把“检索后生成再校验”作为区别。跨版本自动恢复属于扩展机会，不能借已实现的固定输入内完整性证明该扩展已完成。

当前“完整义务编译与校验”更容易形成边界清晰、可量化的独立技术主线；构建方向以关系演进的具体一致性约束形成另一候选主题。两者均未确认专利创造性。

若形成申请，方法、系统、电子设备和存储介质表达同一实质技术组合，不把这些载体分别列为独立创新。本体可用于表达实体类型和约束，当前不将本体、图谱或通用模型本身列为发明点。

## 9. 两轮退款构造实施例

本节全部为解释机制的构造场景，不是实际业务运行或实验结果。测试使用隔离订单、支付模拟服务、受控身份、只读账本核对及明确的异步等待截止条件。

### 第一轮：从全额退款增加部分退款

独立规范规定：已付100元可以依次退60元、40元；并发两笔80元时恰好一笔成功，另一笔因可退余额不足被拒绝；重复请求不重复退款；支付和账本中的业务标识与金额一致。上述是场景条件，实际义务编译还会增加规则、范围项和正反例，不能直接将其数量写成实现中的义务行数。

结构画像定位订单、支付、账本及权限相关实体。历史 `TC-9@T1` 引用了 `US-17`，但只断言“退款成功”。它可以产生 references，不能据此认为验证了重复请求或部分退款条件。

若 `TC-9@T1 asserts AC-2` 被拒绝，同一端点修订重新召回或调用模型不能重置该决定。完整义务集合仍保留 AC-2；缺少可复用资产时生成补充用例或显式缺口。

分包时保留并发与余额的联合义务，金额规则随包携带。不能将“恰好一笔成功”弱化为“退款总额不超过100元”，因为两笔均被拒绝也满足后者。生成校验必须保留原判据。

当前已有生成、审阅、脚本和目标绑定基础。完整目标方案是在取得适用执行证据后逐义务判断，再进入发布流程；不能将本例写成当前系统已自动完成正式放行。

### 第二轮：改为异步回调并修正历史测试

新增回调文件与文档修订形成新来源清单和画像候选。即使新增文件没有出现在旧检索结果里，原查询范围变化也需要影响评估，旧上下文不能据空命中维持原适用性。

`TC-9@T2` 新增“重复相同回调后账本仍只有一笔60元”的明确预期。端点修订变化后，旧拒绝不能作为永久黑名单；新关系重新评估和审阅。原接受关系也不能不经检查迁移。

若目标构建 B2 出现支付退款60元而账本记录两笔60元，固定判据应判失败。若动作已发出但结果无法确认，保留 unknown，不盲目重发退款。修复形成 B3 后，使用新的计划、隔离数据和执行证据重新判断；B1/B2 的历史观察仍保留。

自动将这些新观察归约为逐义务正式通过、解除缺口并形成发布决定，是尚未全部贯通的后续链路，不作为本例证明的已实现效果。

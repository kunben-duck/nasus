## 立项概览

### 发明要解决的问题

AI Coding 缩短了代码生成和修改的操作路径，但一次修改是否影响其他模块、现有测试是否仍适用、运行结果能否支持当前版本上线，仍需要对系统整体进行持续判断。本方案围绕“这次变更是否真的准备好上线”组织技术链路：

**基准画像 → 来源变化 → 影响及失效范围 → 本轮必验义务 → 集成验证资产与计划 → 目标版本执行证据 → 发布准入 → 画像演进。**

画像是代码、需求、测试、执行观察和质量规则之间的版本化知识及证据模型。它随变更持续产生新修订；每次分析、执行和准入使用明确冻结的修订。持续演进与单轮输入固定共同成立。

“快速”的实现路径是复用仍适用的系统知识和测试资产，减少无关重建、重复生成及无关回归；必须验证的行为不能因时间、模型上下文或计算预算不足而消失。信息不足时扩大验证范围或要求补证，不能把较小测试集合直接等同于充分验证。

### 拟论证的核心贡献

拟保护的重点是：**将画像及查询范围的依赖变化，传递为验证依据的失效和本轮必验义务变化；再将这些义务与目标构建的执行证据绑定，在准入时重新检查适用性，最后把经过治理的结果纳入下一轮画像。**

其中，查询范围依赖用于发现“原来没有命中的新增资料也可能改变结论”；固定必验集合用于约束增量选测和生成；证据版本绑定用于防止旧构建结果、不同执行批次或不完整观察拼成当前版本通过。各环节以可检查的修订、摘要和状态衔接，不依赖模型自行宣称完整或通过。

### 立项建议与不确定性

建议围绕上述具体组合继续立项论证。依赖图增量更新、变更影响选测、测试生成、质量门禁和证据追溯分别已有公开基础；将它们串成流程本身不足以证明区别。应重点核对失效传播、查询范围依赖、义务保持和证据适用性之间是否存在可论证的技术制约关系，见第一、三部分。

当前项目已具备来源差异、部分依赖追溯及失效、约束生成、计划准备、构建绑定、运行观察归档和发布阻断等基础。**完整自动增量、正式执行到业务覆盖再到发布准入的链路尚未全部贯通。**主体同时给出现有机制和可实施的完整设计，每步标明状态，不能据局部验证宣布全链通过。

### 阅读与状态口径

- **已实现且有对应验证记录**：存在代码及范围相符的历史验证记录；不等于本轮重新运行或全项目验收。
- **部分实现**：组成机制已有实现，但自动衔接、范围或正式消费链仍不完整。
- **可实施设计**：给出明确输入、规则、输出及异常处理，尚无完整实现验证。

AI Coding 是主要应用场景，方法不依赖代码必须由 AI 产生。本文用于公司内部技术及知识产权评审，不填写未经确认的申请人、发明人及申请日期，也不将历史口头说明或仓库推送状态直接写成“未公开”的结论。资料核查截止日为2026年10月13日。

## 一 背景和现有技术

### 1 高频变更与系统级验证之间的缺口

软件变更往往跨越接口、状态、持久化数据和外部依赖。AI Coding 可以围绕局部任务生成实现及单元测试，但局部测试成功并不自动回答既有业务链是否受损。以退款为例，处理函数修改可能同时影响支付回调、订单状态、累计退款金额和权限控制；仅验证接口返回成功会遗漏重复记账等集成问题。

每轮都从头阅读代码、检索需求和重建测试成本较高；直接沿用上一轮理解又可能使用已失效的关系、规则或执行结果。项目需要保存可以逐轮维护的系统认知，同时知道哪些知识仍适用、哪些必须重评估，以及新一轮必须取得哪些证据。

### 2 主要技术难点

| 难点 | 产生根源 | 本方案需要作出的可检查处理 |
| --- | --- | --- |
| 变化识别不可靠 | 文件缺失可能来自删除、过滤、权限变化或采集失败。 | 利用同范围完整采集证明区分真实增删与未观察到。 |
| 影响范围遗漏 | 只跟踪命中的文件，无法发现新增文件改变空查询或检索排序。 | 同时登记实体依赖、命中证据及完整查询范围依赖。 |
| 历史认识失效 | 同名对象、变化后的端点与旧审阅结论混用。 | 用稳定身份和精确修订判断沿用、重审及未知。 |
| 快速与完整性冲突 | 选测、检索排名和预算控制可能删去重要行为。 | 先固定必验义务，预算仅裁剪可选项；不能容纳时阻断。 |
| 验收预期循环自证 | 从现有代码生成预期，再用该预期验证相同代码。 | 将独立批准的需求预期与实现观察分开管理。 |
| 执行证据错配 | 旧构建、变化的实例、不同环境或批次结果被混用。 | 固定计划与实际目标，逐项核验构建、环境及执行身份。 |
| 上线判断失真 | 工具完成、测试数量、平均分或人工批准掩盖失败与未知。 | 以义务和有效证据判断硬性条件，并独立检查治理条件。 |
| 反馈污染后续画像 | 测试观察或模型推测直接升级为正式业务规范。 | 观察、候选、审阅和正式基线分层，保留历史及回退路径。 |

### 4 拟解决的技术问题与比较方法

在来源连续变化、依赖关系不完全、生成及执行资源有限的条件下，如何保持“本轮变更—必须验证的行为—当前目标上的有效证据—准入结论”之间的一致对应，并使每轮结果能够支持下一轮分析。

单篇文献是否披露完整组合，与多篇文献是否给出组合启示，需要分别分析。后续对照应拆解每项必要特征及其相互作用，而不是用“未找到完全同名方案”替代论证。当前比较用于确定具体技术交底范围，不预设授权结果。

<a id="architecture"></a>

### 1 总体结构与系统边界

![图1 滚动画像驱动集成验证和发布准入的总体闭环](./assets/figure_1_architecture.png)

图1中的处理器可以部署在一个服务内，也可以分为来源采集、画像维护、质量规划、执行和治理服务。数据库保存不可变修订元数据、依赖及决定；私有对象存储保存原文、脚本、响应与日志；检索索引是可重建投影。模型负责提出关系、范围和资产候选，程序规则负责身份、完整性、状态与准入检查。

本文的“集成验证”针对模块、接口、数据状态、消息及外部依赖协作后的可观察行为。构建成功、单元测试成功、导航成功或请求成功，都不能单独证明业务集成行为符合验收条件。“发布准入”指允许目标版本进入受治理的发布流程，不表示本系统已经执行生产部署，也不等于保证不存在任何缺陷。

核心对象分为下列逻辑契约。字段表描述本方案的最小语义，现有实现可能拆为多个对象；标记为设计的组合对象并非宣称已有同名 API 或数据库表。

| 对象 | 核心字段 | 作用及不变量 |
| --- | --- | --- |
| 来源修订 `SourceRevision` | project、binding、tracked_ref、revision、manifest_hash、inventory、capture_status | binding 区分仓库及跟踪范围；多源版本以组合清单固定，不能只固定一个主仓库。 |
| 画像修订 `ImageRevision` | image_id、parent、source_manifest、members、relations、evidence_refs、hash | 发布后不可变；当前指针与原画像正文分开保存。 |
| 关系及审阅 `RelationRevision` | endpoint_ids/revisions、kind、source_refs、review_revision、decision | 代码事实、语义候选、独立规范与运行观察保留各自来源和权限。 |
| 差异 `ChangeSet` | before/after_pins、file/member_deltas、unresolved、scope_proof、hash | 没有同范围完整性证明，不把单侧缺失判成确定增删。 |
| 派生与查询依赖 `DerivationScope` | artifact_id/hash、parents、image_pin、input_digest、source_members、query_scope_fingerprint | 既记录正向命中，也保留空结果及查询来源范围。 |
| 影响及失效 `ImpactAssessment` | change_pin、graph_pin、affected、reasons、unknown_scope、invalidation_scope、hash | 区分有界闭包验证完整与全项目影响完整；失效事实不改写历史。 |
| 独立验收修订 `AcceptanceRevision` | constraint_id、source_pin、preconditions、action、observation、expected、approval_revision | 预期来自明确批准的规范，不能由本次执行结果反向填充。 |
| 本轮义务集合 `VerificationObligations` | round_id、image_pin、policy_revision、rows、global_rules、unresolved、digest | 每行有来源、独立判据和进入必验的理由；固定后不能被选测或生成缩小。 |
| 资产适用决定 `AssetApplicability` | asset_revision、obligation_refs、endpoint_pins、decision、reason | 区分可复用、需修改、需重审和不可用；复用资产不授予执行通过。 |
| 执行计划 `RunPlan` | obligation_digest、cases、scripts/reviews、source_pins、build/environment/data、expected_evidence、digest | 固定全部用例、步骤、判据及目标；执行时不得拼装 latest。 |
| 执行观察及证据 `ExecutionEvidence` | plan_pin、attempt_id、case/step/obligation、request_hash、response_refs、build/environment_refs、status | 原始观察与正式验证状态分开；同一结果集合不得跨批次拼接。 |
| 准入及反馈 `ReleaseAssessment` / `FeedbackRevision` | target、policy_pin、obligation_digest、evidence_set、blockers、approval、expected_head、feedback_refs | 决定可以历史复核；新输入需新评估，正式基线提升需独立治理。 |

摘要采用版本化的规范序列化和抗碰撞散列，字段顺序、字符编码、数值类型及集合排序规则固定。摘要能检测所保护字节或字段不一致，不能证明业务语义正确，也不能单独证明某个响应来自声明的真实目标。

### 2 S101 建立基准画像

**输入：** 项目来源绑定、代码提交、需求及历史测试修订、可用运行记录和批准规则。来源可以缺少需求或历史测试，但必须明确记录缺口；不能据代码现状补造业务规范。

**处理：** 固定每个来源的身份、范围、修订及原始内容，抽取模块、API、数据对象、业务规则、测试和证据。用稳定实体 ID 关联代码调用、数据访问、需求实现和测试验证关系。结构观察与语义候选分开，候选经适用的审阅后才成为可消费关系。原文定位、实体修订及关系端点随画像归档。

独立验收判据由需求或规则的批准修订确定，至少包含前置条件、操作、观察对象与预期结果。代码观察可以指出“当前返回200”，规范可以要求“非所有者返回403且不得记账”；二者冲突应形成待验证问题，不能将观察自动提升为预期。

**输出：** 不可变基准画像 I0、来源组合清单 M0、验收与规则修订，以及已知缺口。候选画像、已批准的版本工作画像和当前正式基线指针分别保存。候选可用于调查和草案分析；成为正式RunPlan及准入依据前，须取得对应消费批准。工作画像获批不等于应用已经上线或画像已晋级项目正式基线。

**异常：** 原文缺失或摘要错误则拒绝接纳；身份冲突进入待合并；缺少关键判据保留未知义务。相似代码、模型置信度和历史通过记录均不能代替批准规范。

**实现状态：部分实现。** 来源归档、画像修订、成员与来源追溯、独立验收批准已有实现及验证记录；完整自主调查、所有语义关系和版本治理仍有未完成范围。[I1](#impl-i1)[I4](#impl-i4)

<a id="s102"></a>

### 3 S102 接收变化并形成新修订

**输入：** 同一来源绑定的旧修订 R0、新修订 R1，原画像 I0，以及代码、需求、测试或环境契约变化事件。AI Coding 的提交或合并可以触发这一过程，事件本身不授予正式发布权。

先形成新的来源清单，保留旧清单不变。比较双方全部已采集路径及内容摘要：共同路径摘要相同为未变，不同为修改；单侧路径仅在另一侧的同范围完整目录采集能够证明不存在时，才判为新增或删除。排除规则变化、读取失败、来源权限变化等分别记录为范围缺口或访问失败。权限不允许时终止读取，不把它伪装为文件删除。

唯一内容匹配可提出改名候选，但不自动继承实体身份或旧审阅。进一步比较画像成员时，应区分源文件变化、实体修订变化和仅索引投影变化；它们不直接等同于业务行为变化。

**异常：** 缺少完整采集证明保留 unresolved；双修订属于不同 binding 时拒绝直接比较；并发刷新使预期清单失效时重新读取后产生新请求。模型、解析器或检索索引升级分别记录其影响，不能静默重写业务事实。

**实现状态：部分实现。** 手动按来源刷新、明确 Git ref、文件及代码成员差异已有实现；自动事件调度、完整实体迁移和增量重建尚未全部完成。[I2](#impl-i2)

### 4 S103 传播影响并判定失效

![图2 双修订差异、依赖传播、失效与新画像](./assets/figure_2_dependencies.png)

**输入：** ChangeSet、I0 与新画像候选各自的对象及关系修订、派生图、查询范围及当前审阅事实。

图2包含两类不同依赖：一类是接口调用、数据读写、消息契约等系统依赖，用于识别可能受影响的业务；另一类是某个上下文、测试方案或覆盖结论依赖哪些来源和上游工件，用于判定既有分析是否仍能使用。后一类依赖闭包完整，不代表前一类业务影响已全部发现。

查询范围指纹固定原上下文输入摘要、画像摘要及全部来源成员，包括当时未命中的来源和采集缺口。新增文件可能改变原来为空的查询或 top-k 排名，因此不能仅扫描 selected hits。对已登记的 context、scope、generation、case、coverage、mapping 等节点，验证完整父集合、摘要及无环依赖，再追踪受变化影响的派生产物。

业务影响传播采用以下可实施规则，与派生产物失效分开计算：先以变化文件定位变化成员；删除成员保留旧图的身份和端点，新增成员从新画像候选提取并固定来源，身份不明时保留未知。在旧、新冻结关系图中分别从这些成员出发，再按有证据的实体对应合并影响候选，路径保留所属图的修订，不能拼出从未存在的混合拓扑。调用边按“调用者→被调用者”登记，被调用者变化时反向追踪调用者；依赖边按“消费者→提供者”登记，提供者变化时追踪消费者。变化成员所属模块用于扩大边界；写入的数据结构或消息契约变化时，纳入相应读写者或订阅者。对受影响成员再查询已批准的验收关联、历史用例及故障保护项，形成进入 S104 的候选及原因路径。未能关联到批准判据的变化形成待调查/待补判据项，不能直接从实现推导出正确预期。

采用确定顺序的有界广度遍历，记录关系类型、方向和前驱；跨入无身份映射、无修订证据或不支持的动态边时标记 unknown。达到跳数/节点界限且仍有未展开邻居，先扩大为相关模块的全部已知验证对象；模块边界也不明确时扩大为系统范围。范围扩大只是保守补救，关键未知未解决时仍不能声称影响完整或准入。现有代码支持有限类型的静态遍历，数据/消息及完整跨源业务传播是目标设计。

已有关系按端点身份和修订分流：精确同版的适用否定继续排除；端点改变则重新审阅；身份不明不得自动继承。排除在候选截取之前执行，避免适用否定占用 top-k 后丢失其他支持材料。

**输出：** 受影响对象、失效工件、原因路径、未知范围及重评估任务。失效事实绑定精确画像修订的当前使用，旧画像不能仅靠新建 Context ID、换预算或重新包装恢复适用；新画像必须重新核验来源和依赖后取得自己的适用状态。历史正文和原始决定保持不变。

**异常：** 依赖图超出可完整核验容量时拒绝声称完整；动态调用、公共配置变化或未知外部契约要求扩大到模块或系统验证。预览后新增派生节点使库存摘要变化，则提交前重新计算。未知范围若仍影响关键验收，阻断后续准入。

**实现状态：部分实现。** 查询范围登记、来源反查、有界派生闭包、画像当前使用失效已实现。当前算法对来源变化保守影响整个固定上下文派生集合，仍明确 `impact_complete=false`；完整项目细粒度传播和自动重建属于设计。[I3](#impl-i3)

def assess_change(before, after, image, candidate_image, dependency_snapshot, policy):
    require_same_project_binding(before, after)
    verify_archives_and_current_access(before, after, image, candidate_image)
    require_image_source_pins(image, before, candidate_image, after)
    delta = []
    for path in sorted(union(before.paths, after.paths)):
        if path in before.paths and path in after.paths:
            kind = "unchanged" if before.hash(path) == after.hash(path) else "modified"
        elif path in after.paths:
            kind = "added" if before.proves_absence(path, after.scope) else "unresolved"
        else:
            kind = "deleted" if after.proves_absence(path, before.scope) else "unresolved"
        delta.append((path, kind))

    roots = roots_for_source_and_query_scope(dependency_snapshot, before.binding)
    # 查询范围包括空召回；不能只用历史命中的文件定位 roots。
    graph = verify_complete_bounded_closure(roots, dependency_snapshot)
    affected = conservative_derivation_impact(graph, delta)
    business_scope, unknown = expand_business_scope(image, candidate_image, delta, policy)
    if unknown or has_unresolved(delta):
        business_scope = broaden_scope(business_scope, policy)
    return freeze(
        image_pin=pin(image), candidate_image_pin=pin(candidate_image),
        before_pin=pin(before), after_pin=pin(after),
        delta=delta, graph_digest=graph.digest, affected=affected,
        business_scope=business_scope, unknown_scope=unknown,
        unresolved=[item for item in delta if item[1] == "unresolved"],
        dependency_inventory_digest=dependency_snapshot.digest,
    )

### 5 S104 确定本轮验证义务

**输入：** 新画像候选、变更与影响评估、独立验收修订、历史失败和发布风险策略。

将本轮必须获得证据的行为定义为集合 O：

`O = 新增或变化行为义务 ∪ 直接影响历史行为义务 ∪ 策略要求的间接影响义务 ∪ 必须保护的历史故障义务 ∪ 适用全局规则义务`。

每行义务具有稳定标识、来源约束及修订、适用目标、四字段判据、进入集合的原因和关键性。按同一语义身份及修订去重，同时保留多个进入理由；不能仅因文本相似合并不同权限或状态条件。缺少预期的义务仍占据分母，状态为待补判据。

O 中的全局规则义务可以同时引用多条行为义务及资产，原标识只计一次；每行及其子检查清单在本轮固定后，不能通过重分组改变分母。间接影响按固定风险策略分类：关键流程、公共契约、高风险失败模式进入必验；其他候选可以排序进入可选集。低置信关系不自动证明存在缺陷，也不能证明没有影响；关键路径上的不确定性要求补充调查、扩大验证或保留阻断。

**输出：** 带摘要的 O、本轮风险与未知项、可选回归集、被排除对象及排除理由。任何排除都不能删除政策已经要求的义务。当前分母是本轮义务数量，不表示全系统需求已被穷尽。

**异常：** 依赖不明扩大验证；无法在预算内满足必验集合时延期、补证或阻断。零义务不能自动变成发布成功，必须有可信的无行为变化判定及仍适用的策略必跑项；本实施方式默认需要显式复核。

#### 7.1 准备与实际目标核验

RunPlan 固定全部输入摘要、用例/步骤/判据和每项义务所需观察项。计划中的构建声明先视为声明；随后独立绑定实际构建产物，验证来源集合、构建定义、工具链与产物字节。多仓库目标必须核对完整来源组合，不能用一个主产物的成功覆盖其余仓库。

运行环境保存实例身份、挂载产物、依赖服务及配置契约的摘要。执行前和关键请求前后核对实际目标；实例更换、构建替换或依赖变化，使原计划不再满足本次可信验证条件。仅响应中返回“build=B2”不足以证明目标身份，需受控部署记录、独立探测或可信执行代理提供与实际挂载产物相符的证据。本实施例使用受控本地测试环境及实际产物检查。

#### 7.2 数据、授权和派发生命周期

测试数据清单按用例固定前置状态、资源命名空间及准备/清理方式。准备与清理分别授权；准备返回且经校验的资源 ID 才能用于后续步骤和清理，不允许模型构造任意生产对象标识。身份 fixture 通过受控认证适配器配置权限，脚本不持有可自由替换的凭据。

在发送有副作用的操作前，持久记录 plan、attempt、job、资源范围及当前 owner/epoch。执行者在有效租约及独立授权范围内执行；恢复只能继续原状态机允许的动作。没有回执且操作可能已经到达目标时记录未知，先查证或建立独立新批次，不自动重发同一退款请求。数据库记录与外部网络副作用并非一个原子事务，不宣称 exactly-once。

#### 7.3 原始观察、证据归集和状态提升

保存实际发送字节的摘要、原始响应及其元数据、日志和目标验证记录。接纳端从原响应重新计算断言，不直接接受 Runner 自报 passed。按原计划逐项核对 job、case、step、obligation、oracle、build、environment 和 attempt；跨批次、跨构建的成功记录不能拼成一轮通过。

| 目标执行 executed_on_target | 原计划、实际目标、环境/数据和授权均可验证，并有对应运行事实。 | 已执行可以失败或中断。 |

**输出：** 原计划下的一次证据集合、逐义务状态及未完成项。正式通过分子只统计不同义务 ID，且每项均满足其固定证据要求；重复响应和重复用例不得增加分子。

**异常：** 摘要不符、缺失物理工件、目标不匹配、计划撤回和跨批次拼接均拒绝进入有效证据集合。环境准备失败与业务断言失败分开；测试结束不保证清理成功，清理异常另行处理并限制后续复用。

**实现状态：部分实现。** 已实现 prepared RunPlan、原生构建及完整来源绑定、受限目标核验与 HTTP 执行组件，以及原响应核验、逐用例观察归档和持久登记。当前构建实测集中在 Java/Maven 等明确范围；观察登记仍保留正式覆盖未授予的状态。完整公开派发、生命周期和真实业务覆盖到发布的衔接尚未全部完成。[I6](#impl-i6)[I7](#impl-i7)[I8](#impl-i8)[I9](#impl-i9)

### 8 S107 计算发布准入

**输入：** 固定本轮 O、目标构建与环境、完整证据集合、质量政策修订、风险与缺口、正式审批及预期基线头。

首先检查本轮输入是否仍适用；其次按义务核对必需证据；最后处理审批与基线冲突。硬性条件优先于综合分数。必验行为存在有效失败，或来源、目标、原始证据完整性无法核验时，不允许以高分或人工批准抵消。

本实施方式把质量评估、操作批准、正式决定与部署动作分开。质量评估满足条件只表示可进入发布审阅；执行发布或基线提升仍要求正式决定及对应授权。非关键风险可以由固定策略归为条件项，但 `conditional` 不在本文严格准入实施例中自动转换为 ready，也不能绕过必验缺口。

| 判定 | 条件及后续行为 |
| --- | --- |
| blocked | 必验失败、关键依赖失效、目标错配、证据损坏或策略硬阻断；保留原因，修复后创建新输入重新验证。 |
| needs_evidence | 没有确定失败但关键义务缺判据、缺运行结果、结果未知或范围无法确认；补证前不得准入。 |
| awaiting_governance | 质量条件满足，但批准、合并或预期基线头尚未满足；保持等待，不表示已经发布。 |
| ready | 全部本轮必验项有适用的有效通过证据，硬阻断为零，治理条件与提交前复核均满足。 |

上述为完整方案的逻辑状态；当前产品还保留 `conditional` 等既有状态，不能将表中名称当作已上线 API 枚举。产品既有评分和“未知质量阻断”提供基础，完整逐义务证据消费仍需贯通。

发布评估摘要固定义务分母、计划/目标/政策、所用证据及原因。正式决定提交时在受控事务内重验画像当前使用状态、验收批准、来源/构建/环境适用性、审阅头和 expected head。若生成或执行后输入改变，则拒绝沿用旧确认，重新形成评估。只改变无关分支且不改变本轮固定目标及依赖，不应凭时间戳使全部历史结论失效；适用性必须有明确目标与政策。

**输出：** 可追溯的准入评估及正式决定，或明确阻断/补证项。数据库中的决定、审计和事件同事务提交；对象存储预写可能留下孤立对象，需另行回收。发布准入并不执行生产部署，画像指针回滚也不等于应用部署回滚。

**实现状态：部分实现。** 已有确定性质量评估、正式决定和批准分离，以及未知质量即使获批也不能提升基线的门禁。不能将当前评分输入中的旧 Run 统计等同于本文完整 O 的目标证据校验器。[I10](#impl-i10)

#### 10.1 初始系统与可观察条件

I0 描述订单服务、退款服务、支付适配器、退款账本和权限校验。初始功能支持全额退款，批准规范包括“只有订单所有者可以申请”“同一业务退款只能成功记账一次”“成功退款总额不得超过实付金额”。画像保存它们与入口、数据对象、历史用例和脚本之间的关系。

构造测试环境含订单 API、隔离支付模拟服务及只读账本查询。支付服务按 business_refund_id 返回可核对的交易 ID；账本查询返回对应订单的成功记录及总额。受控身份 fixture 产生所有者 U1 和非所有者 U2 的会话，由认证适配器绑定到请求；这是目标实施方式，不能声称现有通用 HTTP 脚本已支持任意 Authorization 注入。

每个用例使用独立订单及数据命名空间，默认实付100元。异步验证采用可配置的30秒截止时间与有界轮询；截止后仍未能确认的状态保留未知或执行异常。准备与清理均有独立记录，只有原准备结果中的资源可以清理。支付模拟服务的行为不是生产支付渠道保证。

#### 10.2 第一轮 V1 增加部分退款

AI Coding 任务将全额退款扩展为部分退款，形成代码提交 C1 和新需求修订 A1。A1 独立批准后规定：有效金额为正数且不超过剩余额度；相同请求键和金额重放返回同一退款业务标识；相同键但不同金额拒绝；未登录返回401，非所有者返回403且不得产生支付或记账副作用。

来源差异关联到退款入口、额度计算、支付请求和账本。与变化相关的上下文需重评估；历史所有者、幂等和金额规则仍经适用性核验后使用。新画像候选固定这些来源，并据此形成 O1，而不是直接把 I0 的通过率带入新版本。

| 义务 | 来源及进入理由 | 必须获得的集成观察 |
| --- | --- | --- |
| O1-01 合法部分退款 | 新需求，直接变化行为 | 对隔离订单 D1 退60元；支付侧成功一笔60元，账本一笔60元，订单状态为部分退款。 |
| O1-02 剩余额度及状态 | 新需求，订单与账本影响 | 同一用例内再退40元；累计100元、两笔业务退款，订单转为全额退款完成。 |
| O1-03 非法金额与超额 | 新边界、全局金额规则 | 在独立前置状态下分别测试0、负数及超过剩余额度；拒绝且无新增支付或记账。 |
| O1-04 幂等重放及冲突 | 历史幂等规则，支付契约影响 | 同键同金额返回原业务标识且只记一次；同键不同金额拒绝且无新副作用。 |
| O1-05 权限及认证 | 策略必验的历史保护 | U2 请求返回403，缺认证返回401；支付及账本均无新增记录。 |
| O1-06 并发及总额不变量 | 风险扩展、全局规则 | 两个不同键各申请80元；最终恰一笔业务退款成功80元，另一笔因余额不足被拒绝；支付与账本按同一业务标识一致且总额80元，截止仍不明则未知。 |

O1 有6行义务：金额全局规则的义务标识在本例映射到 O1-06，其他资产同时携带该规则引用，分包复制引用不增加第7个分母项；其固定观察清单还包括各相关用例的金额核对。O1 不是只需6条请求。每行保存完整子检查清单；例如 O1-03 的三种边界必须各有观察，O1-05 的401与403不能互相替代。候选用例可覆盖多行，一行也可映射多个用例，只有其固定观察清单全部满足才算该行有效通过。

生成资产时复用历史权限和幂等用例，补充部分退款、剩余额度和并发验证。若候选把403改成200，直接拒绝；如果缺少账本观察或只检查 HTTP 200，则映射审阅要求补充，不认为已完成金额或幂等义务。

新画像候选经独立审阅发布为可消费的版本工作画像 W1。RP1 固定 W1、O1、C1、实际构建 B1、环境 E1、数据清单 F1和脚本/审阅。独立构建及环境核验后在 attempt T1 中执行；每行结果包含原响应和支付/账本观察。假设6行均有效通过、无关键缺口且治理条件满足，则形成针对 B1 的准入决定。发布流程与知识审阅完成后，部分退款规则、关系及资产进入正式画像 I1。这里的“6/6”是构造推演的结果条件，不是已有业务测量。

#### 10.3 第二轮 V2 改为异步回调

第二个 AI Coding 任务新增 `payment_callback_handler`，改变支付结果处理和并行消费方式，产生 C2。新增文件在 I1 的旧检索中从未命中，但它处于被冻结的来源查询范围；新增事实因此触发相关上下文重评估，而不是因旧 hits 中没有该文件就判定无影响。

业务依赖进一步连接到消息标识、回调处理器、退款业务 ID、账本和订单状态。回调语义需要新的独立规范修订 A2；旧关系的端点变化时重新审阅。O2 固定为8行：保留 O1 的六项行为要求，并增加“同一成功回调重复到达不重复记账”和“回调乱序或终态重放不使状态回退”两项。每行仍需按异步方式补全实际观察，不能只增加两个新用例后沿用 C1 的六项旧通过结果。 A2 明确事件顺序：对同一退款先投递 `SUCCEEDED(seq=2)`，再投递 `PROCESSING(seq=1)`，最后重放原成功事件；在支付侧只有原一笔成功交易的前提下，退款保持成功、订单保持对应的部分退款状态、账本仍只有原一条成功记录，不新增支付或记账。事件标识、退款业务标识和序号共同进入固定观察清单。

新画像候选取得本轮消费批准后成为工作画像 W2。RP2 固定 W2、O2、C2/B2、E2及新的数据与执行批次 T2。对独立订单 D2 申请60元，支付模拟服务只有一笔60元交易；同一成功事件重复投递后，错误实现写入两条60元成功账本，合计120元。原响应、相同事件标识、支付交易和两条账本记录共同形成可核验的失败证据。

重复记账同时违反幂等及金额义务，评估为 blocked；无论其他用例通过多少、是否人工批准，均不能据此发布 B2 或将失败候选晋级为正式 I2。失败观察进入风险候选，原规范中的“只记一次”不因执行结果而改为“两次”。

#### 10.4 修复、重新验证与证据复用边界

修复生成 C2′及 B2′，重新计算影响、资产适用性和本轮计划 RP2′。即使 O2 的文字没有改变，新计划仍固定新的目标及依赖；旧计划和 T2 失败不被覆盖。使用新的隔离订单 D3、fixture F2′和 attempt T2′重跑受影响及政策必跑项。

## 三 技术保护点

### 1 核心组合的建议表达

以下为内部交底的候选保护结构，并非定稿权利要求。方法主题以同一轮的修订、义务和证据连续传递为中心：

一种由计算机执行的变更驱动集成验证与发布准入方法，获取具有来源修订、实体关系和验证资产的基准系统画像以及后续来源修订；根据固定双修订及采集范围确定变化，并依据系统关系与派生依赖确定需要重新调查或失效的验证依据，其中派生依赖包含支持证据及查询范围。

针对变化及其影响范围，结合独立验收修订和风险政策形成具有稳定标识、来源及判据的本轮必验义务集合；在保留该集合的条件下，复用适用验证资产或生成补充资产，形成绑定目标代码、构建、环境和数据的执行计划。

获取并核验该计划下的实际执行观察，按义务、判据及同一目标和执行批次形成有效证据集合；依据必验义务是否获得适用证据及是否存在失败、未知或失效条件，确定发布准入状态，并在提交前重验依赖及治理条件；将运行观察和经确认的知识分别回流，形成后续画像修订，保留原始依据及历史结论。

完整链路不是各模块简单并列：上游变化改变哪些依据可以消费以及哪些义务必须重验；中间生成不能改变这些义务；下游只有与这些义务及目标相符的证据才能影响准入；反馈也不能反向改写原判据。删除某个连接约束，可能导致可复现的遗漏、旧证据误用或错误准入，需用第四部分实验检验。

方法保护处理顺序及数据约束；系统/装置保护来源与画像管理、影响和失效、义务编译、验证执行、证据核验、准入及反馈模块之间的输入输出关系；电子设备和计算机可读存储介质承载相同方法的计算机实现。

AI Coding 说明使用场景，不将特定模型品牌或代码生产者作为必要限制。数据库、消息队列、具体语言、SHA算法型号、预算上限和示例阈值可以替换，只要保持相同的完整性、版本和失败处理语义。不得仅用“自动理解”“智能选测”“保证质量”等结果性语言代替可实施机制。

本稿不主张图谱能完备发现任意动态依赖，不主张全局最小且充分的测试集，也不将字段一致、工件未变或历史通过当作业务正确性证明。完整组合的检索及公开披露时间核验仍是申请前的重要工作。

### 1 问题、机制与可验证效果

预期业务作用是减少团队重复理解和核对版本的工作，使开发者更早获得集成反馈，使发布负责人能够看到明确的阻断与补证项。完整归档、重验、全局规则复制和保守扩大范围会增加存储、输入量及等待成本，必须与收益一起测量。

### 2 对照实验设计

实验对象采用固定可运行测试系统中的30组连续两轮变更；每组具有独立审阅的规范、基准画像及注入缺陷清单。包含跨模块接口、数据库状态、权限、异步事件、公共配置和新增文件影响。此为实验计划，30组不是现有完成样本。

比较四类方案：

- **B0 全量回归**：同一冻结测试资产库全部执行；仅作为运行成本与相对缺陷检出基线，不能假设该资产库完备。
- **B1 常规影响选测**：代码依赖与历史覆盖选测，不增加查询范围失效和贯穿义务机制。
- **B2 完整目标方案**：本文 S101—S108，包括独立验收、必验保持、目标证据和准入复验。
- **B3 消融组**：分别移除查询范围依赖、义务保持或目标/提交复验，其他配置不变，观测每个机制的实际贡献。

所有方案使用相同代码、环境、硬件并发、基准测试资产和已批准验收要求。为了区分选测收益与补充生成收益，先用统一冻结测试集比较，再单独比较增量补充生成；后一阶段固定模型配置、提示及预算，每个输入重复3次。用例语义与缺陷分类由两名独立审阅者标注，分歧仲裁，不能由生成模型自评。

时间指标分别记录“变更可见到首个可信反馈”和“变更可见到准入结论”，包含采集、画像更新、模型、数据准备、执行、重验及等待治理的分段时间；人工等待与系统处理耗时另列。对固定同一变更比较冷启动和已有画像的后续轮次，不把一次全量初始化成本藏在基线之外。

质量指标包括：相对于独立审阅义务集合的遗漏率、已知缺陷检出/漏检、错误证据接纳率、正常结果误拒率、错误准入数、未知保留数及人工复核时间。分母、跳过项、环境故障和缺失日志完整报告；样本中零错误不能推广为所有系统均无错误。

### 3 必须保留的负向实验

注入新增文件改变空召回、来源采集缺口、低相似度权限要求、图截断、oracle改写、执行中实例更换、请求已发送但无回执、跨批次拼接、归档篡改、批准撤回和正式头竞争。验证它们分别触发补充调查、范围扩大、拒绝接纳、未知保留或准入阻断。

金额示例中同时核对支付和账本，避免只看接口返回或只看单个数据库字段。对 unknown 分支检查没有自动重发副作用请求；对并发发布检查只有符合预期正式头的决定可推进。测试数量、静态检查通过或 fixture 清理成功均不得替代这些结果。
